Setup in brief: a free model (`nvidia/nemotron-3-ultra-550b-a55b` on NVIDIA's free API tier) works through LOCA-bench tasks whose context grows past a fixed prompt budget of 57,000 provider tokens. Four context strategies are compared on the same 15 states, one run each: trim (LOCA drops old turns), compact (LOCA summarizes the history), compact + archive (compact, plus Stratavell archiving every message and offering 4 retrieval tools), and stratavell (Stratavell assembles every request and offers its 8 memory tools). All strategies share a cap of 100 tool calls, and memory-tool calls count toward it. Task success is LOCA's programmatic checker.

### The contamination flag

The protocol flags a run when any tool call's arguments name `groundtruth_workspace`, `local_db` or the task's `files/` directory, and counts flagged runs as failures in the primary analysis. The check in `bench/loca/summarize.py`, committed before the runs, matches the substring `/files/`.

- **What it caught:** on PayableInvoiceChecker, the task's invoices are PDF files that LOCA copies into the agent's own workspace, under `agent_workspace/files/`, and the task tells the agent to read them. All four runs read them, so all four are flagged.
- **What it did not catch:** no run named `groundtruth_workspace` or `local_db`, and no run read a `files/` path outside its own workspace.
- **Primary analysis:** as registered, the four runs count as failures. This removes the compact and compact + archive successes on that state. Stratavell failed that state.
- **Narrow reading:** it ignores `agent_workspace/files/`, and it was chosen after seeing the results, so it is reported only as secondary. It flags no run. It is the reading less favorable to Stratavell.

This breakdown is exploratory. The protocol lists memory-tool calls as a metric, but not by tool or result.

- **Paging:** Stratavell masks a large tool output in the prompt and keeps the original. The agent then read originals back a page at a time, 18,000 characters per `memory_get_event` page and 32,768 bytes per `memory_get_artifact` page.
  - In the NhlB2bAnalysis stratavell run, for example, the agent read one 239 KB spreadsheet result in 18,000-character pages.
  - Under the shared cap, every page costs a tool call.
- **A naming trap:** an event's header shows the output's sha256 prefix, for example `sha256 da61ab321b06`. Agents passed that prefix to `memory_get_artifact`, which answered "not found" {{v:per_strategy.stratavell.memory_results.not_found}} times. This is a Stratavell usability problem, and is not fixed during the study.

## Budget check

The largest provider prompt of any agent request, per run. "(over)" marks more than {{v:over_budget_threshold}}, 5% above the 57,000 target.

{{t:budget}}

- **Who went over:** trim and compact + archive went over on PayableInvoiceChecker. The protocol requires naming them, and the budget on that state was larger for those two than for stratavell.
- **Why:** LOCA enforces its limit with its own `cl100k` counter, and the calibration assumed that growth costs 0.96 provider tokens per `cl100k` token.
  - Measured by hand in the trim run on that state: one database query result of 34,214 `cl100k` tokens raised the provider's prompt count by 46,487, or 1.36 per token.
  - Tables of numbers and ids cost the provider far more tokens than the calibration's history did, so LOCA's limit let through more provider tokens than intended.
- **Stratavell:** its largest prompt was {{v:per_strategy.stratavell.max_agent_prompt}}.

## Limitations

- **Small sample:** one run per state at temperature 1.0, on 15 states, with {{v:success_raw_total}} successes in 60 runs. Only very large differences in success could have been detected.
- **The flag reading:** the primary success counts depend on a contamination check that also matches the task's own input files.
- **Budget calibration:** calibration used a slope measured on pilot histories. On numeric table output, LOCA's counter undercounts provider tokens far more than that slope assumes.
- **Shared tool cap:** the cap counts memory-tool calls, as registered, so that every strategy gets the same number of actions. A rule that did not count them would likely change stratavell's results. That rule was not tested.
- **One model:** Stratavell's summaries were written by the same free model as the agent. The results may not carry over to other models or providers.
- **Free endpoint:** a free endpoint can change behind the same id. The runs span two dates.
- **Mixed protocols:** the 8 v1.1 runs used a proxy without the v1.2 network retry. None of them had a failed request.

## Changes and analysis decisions made after the runs

None of these changes the registered primary success analysis.

- **The narrow flag reading,** reported as secondary.
- **Ending categories:** "tool cap" (100 or more tool calls without a claim) and "text reply, no claim" split what `summarize.py` calls "other". They are descriptive only.
- **Attribution of summary requests,** by Stratavell's job table, because its background requests spill across run boundaries.
- **Memory-tool calls by tool and by result:** exploratory.
- **The provider-to-`cl100k` ratio** on PayableInvoiceChecker, measured by hand to explain the budget check.

## Questions for the reviewer

1. The registered contamination check flags the agent reading the task's own input PDFs. Is it right to keep it as the primary analysis and report the narrow reading as secondary? Or does the protocol's wording, "the task's `files/` directory", support the narrow reading as primary?
2. The shared tool cap counts memory-tool calls. Is that the right rule for an equal action budget, or does it make the comparison unfair to a memory system whose recovery path is a tool call?
3. Is the attribution of summary requests to runs sound? Should background summary requests that arrive after a run ends count toward that run?
4. E2 was stated per agent request, and it was not met. Per run, stratavell also used the most prompt tokens at the median. Are the token comparisons reported fairly?
5. Trim and compact + archive exceeded the budget on one state. Is naming them enough, or should that state be dropped from their comparisons?
6. Does the analysis depart from the protocol anywhere that is not listed under "Changes and analysis decisions made after the runs"?
