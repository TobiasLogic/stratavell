REVIEW PACKET: Stratavell agent test on LOCA-bench, protocol v1.2 (revision 3)

This file is for an outside reviewer. It is generated by `bench/loca/render.py` from the result files in `bench/results/2026-11-28/loca-v1.2/`, the same source as `docs/agent-test.md`. Please check the claims against the tables and the protocol, and answer the questions at the end.

Revision 3 answers the second outside review, and revision 2 answered the first. Both sets of answers are near the end, before the questions. The frozen protocol follows the questions, verbatim.

Setup in brief: a free model (`nvidia/nemotron-3-ultra-550b-a55b` on NVIDIA's free API tier) works through LOCA-bench tasks whose context grows past a fixed prompt budget of 57,000 provider tokens. Four context strategies are compared on the same 15 states, one run each: trim (LOCA drops old turns), compact (LOCA summarizes the history), compact + archive (compact, plus Stratavell archiving every message and offering 4 retrieval tools), and stratavell (Stratavell assembles every request and offers its 8 memory tools). All strategies share a cap of 100 tool calls, and memory-tool calls count toward it. Task success is LOCA's programmatic checker.

## Short version

- **Bottom line:** in a small study with one model, Stratavell kept all of its agent prompts under the target budget. It did not show higher task success or lower total prompt tokens. Reading archived outputs back took a large share of its tool budget. The results are negative or inconclusive for Stratavell. They do not show that it is worse in general.
- **Scale:** 60 scored runs, 15 states x 4 strategies, one run each, from 2026-11-27T13:40:44Z to 2026-11-28T01:46:25Z. No slot was excluded. Nothing was billed.
- **Success was rare.** 7 of the 60 runs passed LOCA's checker, on 3 of the 15 states.
  - Checker success: trim 1, compact 2, compact + archive 3, stratavell 1.
  - The registered contamination check flags the 4 runs of one state for reading the task's own input files (see "The contamination flag"). Counting those as failures, as registered: trim 1, compact 1, compact + archive 2, stratavell 1.
  - No success difference is significant. The smallest McNemar p-value is 0.500. With 15 states and this few successes, the success comparison is inconclusive, and is not evidence of parity.
- **Tokens per request:** stratavell's mean prompt per agent request was lower than trim's on 12 of 15 states (sign test p 0.035), and higher than compact's on 12 of 15 (p 0.035). E2 is not met.
  - Neither p-value stays below 0.05 after a Holm correction for the three comparisons (0.105), or without PayableInvoiceChecker, the state where the budget was exceeded (0.057).
  - The protocol registered neither check, so both are secondary.
- **Tokens per run:** no difference against stratavell is significant. Stratavell's median run used the most prompt tokens, 1,982,499.
- **Tool budget:** 25 of the 60 runs ended at the 100-call cap. Stratavell's agent made 325 memory-tool calls, 291 of them reading back a page of an archived tool output. In its 6 runs that reached the cap, 35 to 69 of the 100 calls were memory calls, 280 of 600 in all.
- **Expectations:** E1 met; E2 not met; E3 met as registered, not met under the narrow flag reading; E4 met.
- **Budget check:** on PayableInvoiceChecker, trim's largest prompt was 66,708 provider tokens and compact + archive's 60,804, more than 5% over the 57,000 target. Trim was over the target on 3 states, but more than 5% over only on that one. Stratavell's agent prompts stayed under the target on every state. Summary requests are reported separately: on the same state, LOCA's largest was 75,553.

### The contamination flag

The protocol flags a run when any tool call's arguments name `groundtruth_workspace`, `local_db` or the task's `files/` directory, and counts flagged runs as failures in the primary analysis. The check in `bench/loca/summarize.py`, committed before the runs, matches the substring `/files/`.

- **What it caught:** on PayableInvoiceChecker, the task's invoices are PDF files that LOCA copies into the agent's own workspace, under `agent_workspace/files/`, and the task tells the agent to read them. All four runs read them, so all four are flagged.
- **What it did not catch:** no run named `groundtruth_workspace` or `local_db`, and no run read a `files/` path outside its own workspace.
- **Primary analysis:** as registered, the four runs count as failures. This removes the compact and compact + archive successes on that state. Stratavell failed that state.
- **Narrow reading:** it ignores `agent_workspace/files/`, and it was chosen after seeing the results, so it is reported only as secondary. It flags no run. It is the reading less favorable to Stratavell.

- **Paging:** Stratavell masks a large tool output in the prompt and keeps the original. The agent then read originals back a page at a time, 18,000 characters per `memory_get_event` page and 32,768 bytes per `memory_get_artifact` page.
  - In the NhlB2bAnalysis stratavell run, for example, the agent read one 239 KB spreadsheet result in 18,000-character pages.
  - Under the shared cap, every page costs a tool call.
- **A naming trap:** an event's header shows the output's sha256 prefix, for example `sha256 da61ab321b06`. Agents passed that prefix to `memory_get_artifact`, which answered "not found" 17 times. This is a Stratavell usability problem, and is not fixed during the study.
- **Compact + archive** used its 4 retrieval tools 20 times. Its context is managed by LOCA, which does not mask outputs.
- **Volume:** stratavell's agents made 325 memory calls, about 16 times as many as compact + archive's. 291 of them, nearly 90%, read a page of an archived original.
  - This points to the size of the pieces in which archived outputs come back, more than to search quality, as the bottleneck.
  - The study does not show that paging caused the failures. It is a hypothesis for the next test.

### Session isolation

One Stratavell database served all 30 stratavell and compact + archive runs, so a run could in principle have retrieved another run's memory. These checks were added after the outside reviews.

- **In the study's memory-tool replies:** the replies of 16 runs named 199 event or summary ids, all from the run's own session. No cross-session retrieval was observed.
- **A direct test:** `bench/loca/isolation_probe.py` ran the study's Stratavell binary (e22f79d) on a copy of the study database, without a summarizer.
  - From each of the 31 sessions, it asked for the other sessions' data: event ids, summary ids, artifact hashes that only another session holds, and 65 search terms that only another session contains.
  - It also checked each session's assembled context, task state and stats for those terms.
  - Stratavell allows 8 retrieval calls per turn, so the test assembled the context every few calls to start a new turn.
- **Controls:** each session could still read its own event, expand its own summary and find its own unique terms, so the probes could detect access.
- **Result:** every probe was refused or came back clean, except for one tool.
  - `memory_get_summary_lineage` answered all 780 probes that gave it another session's summary id.
  - It returns that summary's structure: kind, level, sequence range, number of source events, and the ids of the summaries above and below it. It returns no summary text and no event content.
  - This is a Stratavell bug, and it is in the released code too.
- **Effect on the study:** none observed. No run called `memory_get_summary_lineage`, and an agent had no way to learn another session's summary id.
- **Database:** no record links one session's data to another's: summary sources, jobs, blob references, search documents, paths, symbols and task items. No event is shared, and no access grant exists.

## Limitations

- **Small sample:** one run per state at temperature 1.0, on 15 states, with 7 successes in 60 runs. Only very large differences in success could have been detected.
- **Floor effect:** every strategy failed 12 of the 15 states. The tasks were mostly too hard for this model under this budget, which leaves little room to see a difference in success.
- **The flag reading:** the registered check is a faulty definition of contamination, because it also matches the task's own input files. The primary success counts depend on it.
- **Multiple comparisons:** the protocol registered no correction. The two sign tests below 0.05 do not survive a Holm correction.
- **Budget calibration:** the target covered agent requests only. Calibration used a slope measured on pilot histories. On numeric table output, LOCA's counter undercounts provider tokens far more than that slope assumes.
- **Shared tool cap:** the cap counts memory-tool calls, as registered, so that every strategy gets the same number of actions. A rule that did not count them would likely change stratavell's results. That rule was not tested.
- **One model:** Stratavell's summaries were written by the same free model as the agent. The results may not carry over to other models or providers.
- **Free endpoint:** a free endpoint can change behind the same id. The runs span two dates.
- **Mixed protocols:** the 8 v1.1 runs used a proxy without the v1.2 network retry. None of them had a failed request.
- **The tool cap is per reply:** three runs went 1 to 4 calls past 100 on LOCA's own counter. A fourth made 101 calls, one of them to a tool that does not exist (see "How runs ended").
- **The component-matched baseline is not fully matched:** compact + archive gets 4 retrieval tools and LOCA's context management, while stratavell gets 8 tools and Stratavell's assembly. As registered, the comparison is between two configurations, not of context assembly alone.
- **Bootstrap intervals:** with this few successes, they are fragile (see "Paired comparisons").
- **Attribution by timing:** Stratavell does not tag its summary requests with the job and attempt. 21 requests were matched by the run's time window, because a retry overwrites the job's start time.

## Appendix: the frozen protocol, verbatim

`bench/review/protocol-agent-loca-v1.2.md`, committed before the first v1.2 run (commit 0b94971). It restates the whole method, and says what changed from v1.1 and v1. Its opening says that v1.1 was cut short "after 9 scored runs". 9 runs were executed, and 8 of them were valid.

# Agent test v1.2 on LOCA-bench: frozen protocol

Status: frozen. This file is committed and pushed before the first v1.2 scored run. It amends `protocol-agent-loca-v1.1.md`, whose schedule was cut short by a network outage after 9 scored runs (see "Why v1.1 was amended"). v1.1 amended `protocol-agent-loca-v1.md`, which was stopped after two scored runs (see "Why v1 was amended").

## Question

A free model works through LOCA-bench tasks with a context budget smaller than the context the tasks produce. Does Stratavell change task success and token use, compared with LOCA's own context strategies and a component-matched baseline?

The reader tests (v1 to v4.2) could not answer this: they ask questions about a fixed, generated session, and the harness decides when to retrieve.

## Why v1.1 was amended

v1.1's schedule started on 2026-11-27 at 13:40 UTC, and 9 runs completed in order. Then the machine lost DNS at about 15:15 UTC, for at least 6 minutes:
- **The ninth run**, CourseAssistantS2LEnv compact + archive, was in progress.
  - Its next 50 requests failed within 82 seconds. LOCA's retries ran out, and it ended the run with "Error: Failed to get response after multiple retries."
  - v1.1 voids a run that an API error ends, but `schedule.py` looked for a message LOCA never writes, and marked the run valid.
- **Every later run failed preflight** in about 1.5 seconds.
  - `preflight.py` downloads a tokenizer file at startup, and the download needs DNS.
  - The scheduler moved on at once. In 3 minutes 52 seconds, all 51 remaining runs and both reruns of each failed this way: 153 attempts.
  - None of them sent a request to the model.
- **The outage rule** said the operator stops the schedule, which depended on the operator noticing in time. Read as written, it would have excluded 51 of the 60 runs.

v1.2 changes these rules and the harness:
- **A void with no model reply does not count toward the two reruns.**
  - An attempt counts once the model has returned at least one reply.
  - A run with no reply shows nothing of how it would have gone, so retrying it cannot select on the result.
  - After 3 such voids in a row on the same run, the scheduler stops for the operator.
- **The scheduler waits for the model.**
  - Before every run, the proxy sends the model a one-line request. While no reply comes within 2 minutes, the scheduler waits, and asks again every 5 minutes.
  - These requests are logged with the tag `ready`, and are not part of any run.
  - The first push of v1.2 only checked that NVIDIA's API host accepted a connection. Before any v1.2 run, the model stopped answering while the host still did, so the check now asks the model.
- **The proxy retries network errors** and NVIDIA's 500, 502, 503 and 504 replies every 30 seconds, for up to 15 minutes, before returning the error to LOCA. That leaves time for a full 7-minute reply inside LOCA's 1,800-second timeout.
- **The tokenizer file is cached.**
  - `setup.sh` downloads `cl100k_base` once, and the sandbox points tiktoken at that copy.
  - Preflight and LOCA, which also loaded the file during every run, no longer need the network for it.
  - The file is the one every run downloaded, checked by tiktoken against the same sha256, `223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7`.
- **API-error detection** matches LOCA's own messages: "Error: Failed to get response after multiple retries.", "Error: Invalid parameter format." and "Error: Request failed with 400 status.". LOCA's context-limit messages are not API errors, and do not void a run.

What carries over:
- **The 8 valid v1.1 runs** are kept as scored runs. The changes act only on failed requests, on runs with no model reply, and on runs that an API error ended. None of the 8 had a failed request.
- **The CourseAssistantS2LEnv compact + archive run** is void, under v1.1's rule as written. It had 27 model replies, so it counts as that run's first attempt, and v1.2 reruns it.
- **The 153 attempts with no reply** are kept and reported, and do not count.
- **Everything else is unchanged:** the model, states, order, budget, limits, strategies, metrics, statistics and expectations.
- **None of the changes depends on any run's result.**

v1.2 runs are named `v1.2-<state>-<strategy>`. A rerun after a counted void adds `-rN`, and a retry after a void with no reply adds `-zN`.

v1 ran two scored runs on 2026-11-27, both on `CanvasArrangeExamS2LEnv` seed 42, before it was stopped:

They showed two flaws:

1. **LOCA discarded every long reply.**
   - LOCA's HTTP client gives up on a request after 60 seconds. This endpoint writes about 60 to 90 tokens a second, so a reply longer than about 4,000 tokens never arrives.
   - LOCA also discards a reply that stops at the output cap, which was 4,096 tokens.
   - In both cases LOCA resends the same request without telling the agent, up to 50 times. In the trim run, 66 of 92 replies were discarded: 40 by the timeout and 26 at the cap. So 72% of the run's requests, and most of its hour, were resends.
   - Every strategy had the same limits, but they doubled the schedule's length and filtered out the model's longer replies.
   - A first v1.1 pilot raised only the output cap, to 16,384. The timeout then discarded 26 of 41 replies, all of which took 67 to 155 seconds. The longest reply received was 3,617 tokens. That pilot was stopped after 31 minutes and is not a result.
2. **The budgets were not equal.**
   - v1 said every strategy gets about 57K provider tokens. That figure came from the pilot task, which has 57 tools.
   - Each strategy counts tokens with its own counter, and the two counters err differently on tool definitions:
     - On this task's first request (149 tools), the provider counted 1.23 times LOCA's `cl100k` count and 0.89 times Stratavell's estimate.
     - LOCA's limit of 59,904 `cl100k` tokens reached 62,928 provider tokens in the trim run.

   - The gap, about 7% here, grows with the number of tools, and it was against Stratavell.

v1.1 also changes the provider, for the same model. OpenRouter's free tier allows 1,000 requests a day, so the 60 runs would have taken 5 to 6 days. NVIDIA's API catalog serves the same model free, with no daily cap. See Model.

The two v1 runs are reported here and are not scored. v1.1 restarts from the first state.

## Benchmark

LOCA-bench (`hkust-nlp/LOCA-bench`, MIT license), commit 8b6fac4, with the patch in `bench/loca/loca.patch`. It is v1's patch plus a longer request timeout:
- **Stratavell mode:**
  - Every message is appended to a Stratavell session.
  - Every model request is Stratavell's assembled context plus its 8 memory tools.
  - Memory-tool calls are answered by Stratavell, and every other tool call by the environment, unchanged.
- **Passive mode:**
  - LOCA manages its own context as usual.
  - Stratavell archives every message and answers 4 retrieval tools: `memory_search`, `memory_get_event`, `memory_expand` and `memory_get_artifact`.
- **MCP servers** are started from preinstalled environments instead of `uv run` and `uvx`.
- **Shared tool cap:** memory-tool calls count toward LOCA's tool-use cap, and every strategy's run ends when the cap is reached.
- **Request timeout:** new in v1.1. LOCA's HTTP client waits up to 1,800 seconds for a reply instead of 60. The endpoint writes about 39 tokens a second, so a full 16,384-token reply takes about 7 minutes.

Run environment, as in `bench/loca/README.md`:
- **Dependencies** are pinned in `bench/loca/requirements-*.txt`, resolved as of the upstream commit date, 2026-04-29.
- **Preflight:** before every run, `preflight.py` starts each MCP server and checks that it lists tools.
- **Sandbox:** every run executes under bubblewrap.
  - The home directory is not visible.
  - No API key enters the sandbox. Requests go through `freeproxy.py`, which adds the key outside the sandbox and forwards only `:free` model ids.
- **Proxy for NVIDIA:**
  - It asks for the reply as a stream and returns it to LOCA as one reply. In testing, NVIDIA closed a non-streamed 16,384-token request after 5.7 minutes without a reply. Streamed, the same request completed in 7 minutes.
  - It sends requests at least 1.6 seconds apart, under NVIDIA's limit of 40 a minute.
  - It retries a rate-limit refusal (HTTP 429) on NVIDIA up to 40 times, waiting 20 to 120 seconds. It never sends a request to another provider.
  - New in v1.2: it retries network errors and NVIDIA's 500, 502, 503 and 504 replies every 30 seconds, for up to 15 minutes.
- **Tokenizer:** new in v1.2. The sandbox loads `cl100k_base` from a copy made by `setup.sh`, so no run needs the network to start.
- **Stratavell:** one `stratavell serve` built from the v1.1 commit, e22f79d, started with a fresh database before the first v1.1 run. It keeps running, with its database, into v1.2, which changes no Stratavell code. Its summarizer is the agent model, through the same proxy. The policy is the default except for the window.
- **Runs** go one at a time, in the fixed order. New in v1.2: before every run, the scheduler waits until the model answers a one-line request.

## Budget

Every strategy gets the same prompt budget, counted in provider tokens, on every state:
- **Target:** at most 57,000 provider prompt tokens per request.
- **Output cap:** 16,384 tokens for every strategy, with the 1,800-second request timeout.
- **Enforcement:** each strategy keeps enforcing the budget with its own counter, but its limit is set per state so that the limit corresponds to 57,000 provider tokens.

How the per-state limits were set (`bench/loca/dump_tools.py`, `measure_calib.py`, `calibrate.py`):
1. For each state, the first request was built in three forms:
   - LOCA's: the task prompt and the environment's tools
   - passive mode's: the same plus the 4 retrieval tools
   - Stratavell's: its assembled first request, with its 8 memory tools
2. Each form was sent once with a 1-token output cap. The provider's prompt count was recorded next to the strategy's own count.
3. Growth from that first request was converted at the pilot's measured rates:
   - **LOCA's counter:** 0.96 provider tokens per `cl100k` token of messages. The two v1 runs measured 0.964 and 0.955.
   - **Stratavell's counter:** 0.95 provider tokens per estimated token. The 8K and 128K pilots measured 0.968 and 0.931.
4. The resulting limits:
   - **LOCA's input limit:** first-request count + (57,000 − first-request provider count) / 0.96. `--max-context-size` is that limit plus 16,384, because LOCA reserves the output cap from it.
   - **Compact's summary threshold:** `--reset-size` is 85% of the input limit. In v1 it was 51,200 of 59,904, or 85.5%.
   - **Stratavell's capacity:** first-request estimate + (57,000 − first-request provider count) / 0.95. The window is the smallest one whose capacity reaches it, with Stratavell's default safety margin and overhead.

## Strategies

All strategies use the same model, prompt, tools, budget and tool cap. Common flags: `-s react --max-tool-uses 100 --max-tokens 16384`. The temperature is 1.0, fixed by LOCA. Per-state numbers come from `budget-v1.1.json`.

1. **trim:** `--max-context-size` from the table.
   - LOCA drops the oldest assistant turns and their results to fit.
   - If one tool output is larger than the budget, it removes everything and the run ends.
   - This is the standard control.
2. **compact:** `--context-summary --reset-size R --max-context-size M`. The agent model summarizes the history at 85% of the input limit.
3. **compact + archive:** strategy 2 with `STRATAVELL_MODE=passive`, using the passive-mode limits. This is the component-matched baseline: the same retrieval, with LOCA's context management.
4. **stratavell:** `STRATAVELL_WINDOW` from the table. Stratavell's assembly with the default policy, plus its 8 memory tools.

A run that reaches the tool cap ends and counts as a failure.

## Model

`nvidia/nemotron-3-ultra-550b-a55b` on NVIDIA's API catalog (build.nvidia.com), free tier. LOCA names it with the `:free` suffix, which the proxy removes. v1 used OpenRouter's free endpoint for the same model.

- **Same model on both:** checked before freezing (see Pilot).
  - Prompt counts were identical on all 45 calibration requests.
  - The same first request gave replies of similar length and the same first tool call on both.
  - The same mid-run history gave the same 50-token reply, word for word, on both.
- **One provider:** every scored run uses NVIDIA. The proxy never switches provider. If NVIDIA becomes unavailable, the scheduler waits until it is back. Runs voided by an outage are kept and reported. They count toward the two reruns if the model returned at least one reply (see Validity rules). A change of provider would be a new amendment, made before any further scored run.
- Run dates are recorded, because a free endpoint can change behind the same id.

## Metrics

- **Headline:** task success from LOCA's programmatic checker (1 or 0), per strategy, paired by state.
- **Per run:**
  - agent and summarizer requests
  - replies cut off at the output cap, which LOCA resends
  - provider prompt and completion tokens, as a sum, per agent request, and as the largest single request
  - compaction events: LOCA's trim and summary events, and Stratavell's assembly reports
  - memory-tool calls, steps and wall time
  - how the run ended: claimed done, tool cap, context lost or other
  - machine load
- **Estimated cost:** tokens priced at a paid endpoint's listed price for the same model on the run date. It is labeled as an estimate, because the free tier does not bill. The prompt tokens NVIDIA reports as cached are recorded and shown next to it.

## Validity rules

- **Void runs:** a run is void when:
  - the preflight fails
  - the run exits nonzero or times out after 6 hours. v1's limit was 3 hours, but with replies of up to 16,384 tokens a single request can take several minutes.
  - LOCA's evaluation does not complete
  - an API error ends the run: the last message is one of LOCA's API-error messages (see "Why v1.1 was amended")
  - the proxy's daily cap is reached during the run, or it returns a rate-limit refusal to LOCA after its 40 retries

  `schedule.py` reruns a void run at most twice. Void runs are kept and their counts are reported. A state whose run stays void after two reruns is reported, and excluded from the paired comparisons for that strategy pair.
- **Voids with no model reply:** new in v1.2. A void run in which the model returned no reply does not count toward the two reruns, and is retried. After 3 of these in a row on the same run, the scheduler stops, and the operator restarts it once the cause is fixed.
- **Daily quota:** NVIDIA has no daily cap. The proxy's own cap is set to 20,000 requests a day, so it should not bind. The scheduler still starts a run only when at least 160 of that day's requests remain.
- **Contamination:** a run is flagged when any tool call's arguments name `groundtruth_workspace`, `local_db` or the task's `files/` directory. LOCA's Python tool can read those paths. Flagged runs count as failures in the primary analysis, and are listed.
- **Budget check:** for each strategy, the largest provider prompt of each run is reported next to the 57,000 target. A strategy whose largest prompt exceeds the target by more than 5% on any state is named in the results, with the states.

## Statistics

With 15 states and one run each at temperature 1, only large differences can be detected. Results are reported mainly descriptively:
- **Success:**
  - success counts per strategy, with the 2 x 2 paired table against stratavell
  - McNemar's exact p-value for each pair
  - a paired bootstrap 95% interval of the success difference
- **Tokens:**
  - provider prompt tokens per agent request and per run
  - paired differences against stratavell, with the median and a sign test
- **Wording:** a difference that is not significant is reported as inconclusive, not as parity.

## Expectations

Unchanged from v1, and reported as met or not met:
- **E1:** stratavell succeeds on at least as many states as trim, and at least as many as compact, minus 1 in each case.
- **E2:** stratavell's median provider prompt tokens per agent request are lower than compact's and lower than compact + archive's. This is the median over states of each state's per-request mean, with paired differences.
- **E3:** stratavell succeeds on at least as many states as compact + archive, minus 1.
- **E4:** at least one trim run ends with context lost: an output larger than the budget removes the whole history. This happened in the 128K pilot.

## Scale and budget

- **Size:** 15 states x 4 strategies = 60 scored runs.
- **Estimate:** the four NVIDIA pilot runs took 4 to 8 minutes and 20 to 52 requests each. Other tasks may need more steps, and a run can use up to 100 tool calls. So the 60 runs should take about 6 to 24 hours and 2,000 to 6,000 requests.
- **After v1.1:** its 9 completed runs took 6.9 to 27.9 minutes and 16 to 113 requests each. At their mean of 10.8 minutes, the 52 runs left take about 9.5 hours.
- **Cost:** $0, on free models only.
- **What this is:** a first measurement, not a definitive comparison. A definitive one would need all 75 states and repeated runs.

## Pilot (not results)

v1's pilot is in `protocol-agent-loca-v1.md`. The v1.1 pilot ran on 2026-11-27 on `CanvasArrangeExamS2LEnv` seed 123, which is not a scored state. Canvas was chosen because it has the most tools (149), and so the largest counter gap. Each run used this protocol's flags and Canvas limits:

| run | provider | requests (agent + summarizer) | replies LOCA discarded | minutes | largest prompt (provider) | how it ended | success |
|---|---|---|---|---|---|---|---|
| trim, first try | OpenRouter | 41 + 0 | 26, all by the 60-second timeout | 31.7 | 55,535 | stopped by the operator | (none) |
| trim | NVIDIA | 52 + 0 | 0 | 7.7 | 58,385 | claimed done | 0 |
| compact | NVIDIA | 19 + 3 | 0 | 4.8 | 49,281 | claimed done | 0 |
| compact + archive | NVIDIA | 24 + 10 | 0 | 5.3 | 49,993 | claimed done; no archive tool used | 0 |
| stratavell | NVIDIA | 19 + 1 | 0 | 4.0 | 39,824 | claimed done; 6 memory-tool calls | 0 |

- **No reply hit the output cap** in the NVIDIA runs, and no request failed.
- **The trim run's largest prompt was 58,385**, 2.4% over the 57,000 target, within the 5% of the budget check.
- **Stratavell stayed below the budget.** Its largest estimate was 44,223 of its 61,932 capacity, and its largest provider count was 0.90 of that, consistent with the calibration.
- **Compact + archive** used no retrieval tool, as in v1's 128K pilot.

**Endpoint comparison,** done before freezing:
- **First request:** the Canvas first request, sent 3 times to each endpoint. Replies were 122 to 228 tokens on NVIDIA and 130 to 212 on OpenRouter, all calling `canvas_canvas_list_courses`.
- **Mid-run history:** step 10 of the NVIDIA trim pilot (48,207 prompt tokens), sent twice to each. All 4 replies were the same 50 tokens, word for word.
- **Reply lengths:** in v1's trim run, 66 of 92 requests were resends of discarded long replies. So its per-request reply lengths (median 4,096 tokens) mostly measure those resends, not a difference between endpoints. The four NVIDIA pilots' median reply was 53 to 172 tokens.
- **Speed:** a streamed 16,384-token reply took 7 minutes 5 seconds on NVIDIA, about 39 tokens a second. The pilots' agent requests took a median of 4.0 to 5.8 seconds.

The pilot also changed the harness:
- **Proxy:** it gained the NVIDIA mode.
- **Request timeout:** raised from 600 to 1,800 seconds.
- **Run order:** unchanged; runs go one at a time.
