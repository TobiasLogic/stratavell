# Benchmarks

This page is generated by `bench/review/render.py` from the raw results in `bench/results/2026-11-26/`. The deterministic tables come from build {{build}}. Prose was written by hand; every number in a table comes from the result files. The experiment log, including failed and superseded runs and API costs, is `docs/experiments.md`. An outside review of an earlier version of these results is answered in "Changes after external review" at the end.

## What these results do and do not show

- **Generated sessions.** The coding sessions are generated with a fixed, scripted trajectory, so no strategy can change what the agent does. The results measure what each strategy keeps available, at what cost and delay. **Task success on real coding tasks was not evaluated.**
- **Built to stress compaction.** The workload is designed around problems that compaction is known to cause: early constraints, exact historical values, large and repeated tool outputs, a changing failure. I designed both the workload and the engine. It is a stress test, not a representative sample of agent sessions.
- **Reconstructed baselines.** B, C and D are reimplementations from published descriptions and source code: a conventional-compaction proxy, a noa reimplementation, and Complexity Trap style masking. They are not the original systems, and B is not Claude Code.
- **Simulated costs.** Prompt-cache costs come from a simulator of Anthropic's documented caching rules, not from provider bills.
- **Modeled latency.** Summarizer latency is modeled in the deterministic runs and measured in the real-model runs.
- **Small samples.** 5 seeds at 64k, 3 seeds at 200k, and 1 to 2 seeds for the real-model runs. No significance tests were run.
- **Benchmarks not run.** CompactionBench is not released, so it could not be run. OOLONG was not run.

## Workload

`bench.Generate(seed, turns)` produces one long coding session per seed.

- **Repository:** a synthetic Go repository of 38 files, including a config file with planted constants and a large file with a planted function.
- **Turns:** each turn has one to three tool calls:
  - file reads
  - whole-file writes
  - `go test` runs with large logs, two thirds of them failing with a changing assertion
  - grep outputs with up to 1,540 lines
- **Planted facts,** asked about at twelve probe points per session:
  - two user ground rules in the first message
  - a later user process rule
  - an architectural decision with a reason
  - a rejected approach with a reason
  - two config values
  - a function name inside a large file
  - the exact assertion message of the currently failing test
- **Size:** a 300-turn session is {{main64k.raw}} million raw tokens. A 400-turn session (200k runs) is {{main200k.raw}} million.

## Strategies

| id | strategy | implementation |
|---|---|---|
| A | uncompressed | engine with every reduction off; a request over capacity counts as an overflow |
| B | conventional compaction (proxy) | at 90% of capacity, summarize everything except the last 8 messages into one summary written from the previous summary plus new history; synchronous; no retrieval |
| C | noa (reimplementation) | Norma's noa algorithm as specified in `docs/research/04-norma-noa.md`: nudges at 0.75 and 0.45 of the limit, a protected tail, tiered blocks, truncation at 0.95; the primary model is assumed to comply with every nudge, and its in-band compression calls are simulated through the same cache model |
| D | observation masking only | rolling mask keeping the last 10 observations |
| E | synchronous progressive summaries | DAG summaries at the soft threshold, blocking (similar to APEC's PEC) |
| F | asynchronous progressive summaries | as E, in background jobs (similar to APEC) |
| G | palimpsest | everything on |

Component-matched variants:

| strategy | what it adds |
|---|---|
| B + pinned user messages | B, plus every compacted user message repeated verbatim after the summary |
| B + passive archive with retrieval | B, plus every message journaled in a palimpsest archive and the memory tools, like the MCP passive mode |
| E + retrieval, F + retrieval | E and F, plus the memory tools and automatic evidence injection |

All strategies in a run use the same summarizer and the same host prompt, tools and cache simulator.

## Metrics

- **completion %:** share of turns whose request fit the window. An overflowed turn is a failed request.
- **input cost:** cache-simulated input cost at Claude Sonnet 5.5 list prices: $2.00 per Mtok uncached, $2.50 for 5-minute cache writes, $0.10 for cache reads.
- **total cost:** input cost, plus the output tokens of C's in-band compression calls at $10 per Mtok, plus summarizer tokens priced at Claude Haiku 5.5 ($0.10 input, $0.50 output per Mtok). The agent's own output tokens are identical across strategies and excluded.
- **Do not compare costs with strategies below 100% completion.** Their overflowed turns were never sent.
- **Reconciliation:** every request, including C's in-band calls, goes through the cache simulator. A run fails if `cache read + cache write + uncached` differs from total input tokens, or if the summed cost differs from the cost of those components.
- **visible %:** the fact's answer key appears in the assembled context.
- **grounded %:** the answer key and its supporting evidence both appear. Only the function-name fact has separate evidence: its body line `w.fsyncGroup(ctx, frames)`.
- **recoverable %:** grounded, or found with its evidence by a fixed retrieval policy. The policy is `memory_search` with a natural query, then `memory_get_event` on the top three hits. Only strategies with memory tools can recover.
- **standing rules %:** over all turns and all user rules already given by that turn, the share where the rule is visible. Rules given later in the session are counted only from the turn they appear.
- **engine p95:** wall time inside `Assemble` per turn.

Read this table as follows:
- **Retrieval drives recovery.** E and F with retrieval recover nearly as many planted facts as G, so most of G's recovery advantage in the main table comes from having retrieval at all.
- **Pins drive standing rules.** Strategies that only summarize lose most standing rules even with retrieval, because nothing puts the rules back in context unless a search happens to hit them.
- **The current failure needs task state.** With retrieval, the summary strategies still miss the latest failing assertion in about a third of probes, probably because the search returns an older failure with the same wording (not verified per probe). G keeps the latest failure in its task state.
- **What remains G's own, against the best matched baselines (E and F with retrieval):**
  - roughly half the input cost, from externalizing oversized outputs, epoch masking and the cache-aware layout (see the ablations)
  - standing rules kept, from pins
  - the current failure kept, from task state
  - no blocking, compared with E
  Completing every turn is not unique: E and F also complete every turn. The B variants do not, because their kept tail cannot shrink.

## Ablations of G, 64k window

300 turns, 5 seeds. Each variant turns one component off.

{{ablation64k.main}}

The largest single saving comes from externalizing oversized outputs at ingestion. Cache-aware ordering is the second: epoch masking instead of a rolling window, and dynamic blocks after the last cache breakpoint. Task state and pins cost little and are what keep the current failure and the standing rules visible.

Synchronous compaction is cheaper and blocks the foreground; asynchronous compaction trades some input cost for no summarization wait. This matches APEC's own result (PEC cheaper than APEC). It is a property of this scheduling and cache layout, not a general law.

## Retrieval-assisted question answering (real model)

At four probe points per session, Claude Haiku 5.5 (via OpenRouter, temperature 0, 600 output tokens) answers each planted question using the exact context the strategy assembled at that point. For strategies with memory tools, the fixed retrieval policy's output is appended when the fact and its evidence are not both visible. This is retrieval-assisted question answering, not an agent evaluation: it does not test whether an agent would decide to search, or with which query.

Three grading dimensions:
- **value recovered** (lenient): the answer contains the key.
- **evidence available:** the context or appended retrieval text contains the key and its evidence.
- **grounded answer** (strict, the headline): the value is recovered and the answer does not hedge ("I don't know", "not shown", "cannot confirm").

### v3: frozen protocol, component-matched (`bench/review/protocol-reader-v3.md`)

64k window, 300 turns, seed 1. The protocol, grader, keys and prompt were committed before the run (commit 2343c4b), and the run is reported as it came out.

{{reader.v3}}

What v3 shows:
- **No QA advantage under matched retrieval.** With comparable retrieval access, G answers about as well as the component-matched baselines; the strict counts are within two questions of each other on one seed. The large QA gaps in v2 below come from G having retrieval and the summary-only baselines not having it.
- **A product flaw:** most strict failures, for every strategy, are hedges on the two config-value questions. The retrieved content showed `RetryLimit = 3` or `ListenPort = 8123` but not the file it came from, so the reader correctly refused to confirm it was `pkg/api/config.go`. Search hits and event pages did not carry the event's file path.
- **Fixed after v3:** search hits, `memory_get_event` pages and injected evidence now include paths, tested in `TestRetrievalOutputsCarryProvenance`. The fix has not been re-measured with a real model, because the remaining API budget was not spent.

## Acceptance targets

| target | result | evidence |
|---|---|---|
| 100% exact recovery of committed, retained events | no failure observed | `Verify` after every engine run reported 100%; tests after repeated compaction and after SIGKILL of a writer |
| 100% preservation of designated protected constraints | no failure observed in runs with pins | standing rules 100% in every G run with pins; specific tests in `engine/engine_test.go` |
| zero silent tool-call protocol corruption | no failure observed | pairing validated on every assembly and again in the adapters; tested only against the documented Anthropic and OpenAI shapes, and live only through OpenRouter |
| zero cross-agent or cross-session leakage | no failure observed in tested configurations | isolation tests, the HTTP test and a four-agent load test; the benchmarks are single-agent |
| zero context-overflow requests | no failure observed | 0 overflow turns in every run of G and its ablations |
| no synchronous summarization in normal operation | met | G's foreground summarization wait was 0 s in every run |
| under 20 ms p95 overhead for small events | met | see Performance |
| under 20 ms p95 lexical retrieval on a representative corpus | met at 3.4k chunks, missed at 13.2k chunks | see Performance |
| at least 50% fewer tool-output tokens | met against summary-only strategies at 64k, partly at 200k | tool Mtok columns above; the brief did not define "unnecessary", so this counts all tool tokens sent |
| lower foreground compaction latency than existing compaction | met against the proxy | G 0 s against B's modeled blocking time |
| no meaningful degradation in task success | **not evaluated** | no real task was solved by any strategy |

## Performance

Measured with `go test` micro-benchmarks and latency profiles (`engine/bench_test.go`). The machine was an 8-core, 16-thread x86-64 laptop CPU with 16 GB RAM, `synchronous=FULL`, Go 1.27.4 and pure-Go SQLite 3.54.1.

| operation | measurement |
|---|---|
| append a small event | 0.56 ms mean per event |
| append a 160 KB test log, background indexing (default) | 36 ms mean |
| append a 160 KB test log, indexing inline | 51 ms mean |
| assemble, 64k window, 45k-token context | 1.35 ms mean |
| assemble, 200k window, 68k-token context | 0.74 ms mean |
| search, 300-turn session, 3.4k indexed chunks | p50 2.33 ms, p95 9.44 ms, p99 11.42 ms |
| search, 1,200-turn session, 13.2k chunks | p50 3.58 ms, p95 33.73 ms, p99 36.30 ms |
| four concurrent agents, 150 turns each | append p95 9.29 ms, assemble p95 9.59 ms, no cross-agent hits |

Search at 13k chunks misses the 20 ms target. The cost is BM25 scoring on the OR fallback in pure-Go SQLite.

## Changes after external review

An outside review of the first published version raised these points. What changed:

1. **noa cost accounting was inconsistent.** Its in-band compression calls (about half its input tokens) were priced with a shortcut that assumed nearly all of their input was cached. They were also left out of the cache-hit numerator. They now go through the cache simulator like every other request. Runs reconcile tokens and cost by construction or fail. noa's reported cost rose substantially as a result.
2. **Strict grading is the headline,** next to lenient and evidence-available counts.
3. **"End-to-end reader test" is renamed** retrieval-assisted question answering. Task success is marked not evaluated.
4. **The standing-rule metric is defined precisely:** only rules already given at each turn are counted.
5. **Baselines are labeled** as proxies or reimplementations.
6. **Component-matched baselines were added:** conventional compaction plus pins, conventional compaction plus a passive archive, and summaries plus retrieval.
7. **Evidence keys:** a fact counts as grounded only when its evidence is visible too. Retrieval in the reader test triggers on missing evidence.
8. **Total cost** adds in-band output and summarizer tokens. **Completion rate** is reported next to cost, and cost comparisons use only strategies that completed every turn.
9. **A frozen-protocol reader run (v3)** was committed before being run. It showed parity with the component-matched baselines and exposed missing file provenance in retrieval outputs, which was then fixed.
10. **Absolute claims softened:** acceptance results say "no failure observed" where the evidence is tests rather than proof.

Still open:
- a real autonomous coding-agent benchmark (tasks executed, patches tested, cost per resolved task)
- stronger model-written summaries for the baselines
- more seeds, and a threshold sweep

## Reproducing

```
go build -o bin/palbench ./cmd/palbench
./bin/palbench -window 64000 -turns 300 -seeds 1,2,3,4,5 -strategies main -out out/main64k
./bin/palbench -window 64000 -turns 300 -seeds 1,2,3,4,5 -strategies matched -out out/matched64k
./bin/palbench -window 64000 -turns 300 -seeds 1,2,3,4,5 -strategies ablation -out out/ablation64k
./bin/palbench -window 200000 -max-output 16000 -turns 400 -seeds 1,2,3 -strategies main -out out/main200k
OPENROUTER_API_KEY=... ./bin/palbench -window 64000 -turns 300 -seeds 1 -strategies G-hybrid -openrouter-reader anthropic/claude-haiku-5.5 -reader-points 4 -out out/reader
python3 bench/review/render.py "$PWD"
go test ./engine -run '^$' -bench . -benchtime 300x
go test ./engine -run 'TestSearchLatencyProfile|TestMultiAgentLoadProfile' -v
```

The deterministic runs give identical results on the same build. The workload, ids and clock are seeded, and the summarizer is deterministic.
