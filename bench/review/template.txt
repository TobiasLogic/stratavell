1. CHANGES SINCE THE FIRST REVIEW
---------------------------------

A. noa cost accounting (review issue A: confirmed and fixed)
- About half of noa's input tokens came from its in-band compression calls.
- Those calls were priced with a shortcut that assumed everything except 2,000 tokens per call was a cache read.
- They were also excluded from the cache-hit numerator. Cost and hit rate were therefore computed on different bases.
- Fix: every request, including in-band calls, now goes through the cache simulator.
- Each run records cache-read, cache-write and uncached totals, and aborts if
  (a) read + write + uncached != total input tokens, or
  (b) the summed cost != the cost of those components.
- noa's cost went up substantially; see section 4.

B. Strict grading is the headline. The QA tables report three dimensions:
- value recovered (lenient)
- evidence available
- grounded answer (strict: value recovered and no hedging)

C. "End-to-end reader test" is renamed retrieval-assisted question answering. Task success is marked NOT EVALUATED.

D. The standing-rule metric is defined precisely: over (turn, rule) pairs, counting only rules already given at that turn. This was already how the code worked; the earlier wording ("turns on which all three rules are visible") was wrong.

E. Baselines are labeled as proxies or reimplementations. B is not Claude Code.

F. Component-matched baselines were added (review question 3):
- B + pinned user messages
- B + passive archive with retrieval
- E + retrieval
- F + retrieval
See section 5.

G. Evidence keys (review issue D): a fact is "grounded" only when its supporting evidence is visible too. For the function-name fact, that is the body line showing fsync batching, not just the name. Retrieval in QA now triggers on missing evidence, not on a missing name.

H. Total cost adds:
- noa's in-band output at $10 per Mtok (Sonnet 5.5 output)
- summarizer tokens at Claude Haiku 5.5 prices ($0.10 in, $0.50 out)

Completion rate is reported next to cost, and cost comparisons use only strategies that completed every turn.

I. A frozen-protocol QA run (v3) was committed before running (bench/review/protocol-reader-v3.md, commit 2343c4b). It tests G against the two component-matched baselines.
- Result: parity.
- It exposed a provenance gap in retrieval outputs, fixed afterwards and re-measured with three free readers in v4 (section 7.0).

J. Absolute acceptance claims are softened to "no failure observed" where the evidence is tests, not proof.

Not done, because of budget or scope:
- a real autonomous coding-agent benchmark (the most important missing experiment)
- stronger model-written summaries for B
- more seeds
- a threshold sweep


2. WHAT THE ENGINE DOES (SHORT)
-------------------------------

- **Journal:** an append-only SQLite journal (WAL, fsync per commit) with content-addressed blobs and a SHA-256 for each event.
- **Context as a view:** the model's context is rebuilt each turn as a view of the journal. In order:
  - summaries, a DAG whose leaves point at exact event ids
  - standing user instructions pinned verbatim
  - a task-state snapshot
  - the recent raw history
  - small per-turn additions at the end
- **Zero-model reductions first:**
  - oversized outputs become previews with a log digest at ingestion
  - exact duplicates and unchanged re-reads become references
  - old observations are masked in batches ("epochs")
- **Background summaries:** published only between requests, with a compare-and-swap check.
- **Emergency fallback:** a deterministic ladder guarantees the request fits without a model call. If protected instructions alone cannot fit, it errors instead of dropping them.
- **Memory tools:** search (FTS5 BM25 plus symbol, path and id lookup, rank fusion), expand, get event, get artifact, task state, lineage and stats.
- **Interfaces:** Go SDK, HTTP API and Unix socket, MCP server, CLI. Adapters for Anthropic Messages, OpenAI-compatible APIs and Ollama.


3. HOW IT WAS MEASURED
----------------------

Workload (bench/workload.go):
- A generated coding session per seed, on a synthetic Go repo of 38 files.
- One to three tool calls per turn: reads, whole-file writes, failing and passing test runs with large logs, large grep outputs.
- Planted facts:
  - two early user rules
  - a later user rule
  - a decision with a reason
  - a rejected approach with a reason
  - two config values
  - a function name in a big file
  - the currently failing assertion
- 300-turn sessions are {{main64k.raw}} million raw tokens; 400-turn sessions are {{main200k.raw}} million.
- The trajectory is scripted, so these are information-availability and cost measurements. NO TASK SUCCESS IS MEASURED.

Strategies:
  A  uncompressed (overflow = failed request)
  B  conventional compaction proxy: one rolling summary at 90%, keep last 8 messages, synchronous
  C  noa reimplementation (model-driven tiered compression; the model is assumed to comply with every nudge; its in-band calls are simulated and priced)
  D  observation masking only (last 10 observations)
  E  synchronous progressive DAG summaries (similar to APEC's PEC)
  F  asynchronous progressive summaries (similar to APEC)
  G  Stratavell
  Component-matched: B+pins, B+archive (passive Stratavell archive with retrieval), E+retrieval, F+retrieval

Summarizer:
- Extractive and deterministic for all deterministic runs.
- Haiku 5.5 in one real-model run.

Pricing:
- Sonnet 5.5 for the primary model: $2 uncached, $2.50 5-minute cache write, $0.10 cache read, $10 output per Mtok.
- Haiku 5.5 for summaries.
- The cache simulator follows Anthropic's documented rules: writes only at breakpoints (max 4), a 20-position lookback, a 512-token minimum and a 5-minute TTL.

Metrics:
- completion %: turns whose request fit the window
- input and total cost (total adds in-band output and summarizer cost)
- visible % (answer key in context)
- grounded % (key plus evidence in context)
- recoverable % (grounded, or found with evidence by a fixed retrieval policy)
- standing rules % (over turn and rule pairs, rules already given)
- fg wait s (foreground summarization wait, modeled for extractive runs)
- engine p95 ms (time inside Assemble per turn; wall-clock, so it varies between runs: G at 64k was 3.14 ms in the original runs and 2.06 ms in the 2026-11-27 rerun)

Hardware: 8-core, 16-thread x86-64 laptop CPU, 16 GB RAM, NVMe; Go 1.27.4, pure-Go SQLite 3.54.1.

7. RETRIEVAL-ASSISTED QUESTION ANSWERING (REAL MODEL)
-----------------------------------------------------

Setup:
- Reader: Claude Haiku 5.5 via OpenRouter, temperature 0, 600 output tokens.
- At 4 probe points, each planted question is asked against the exact context the strategy assembled at that point.
- For strategies with memory tools, the fixed retrieval policy's output is appended when the fact (v2: the key; v3: the key plus evidence) is not visible.
- This is not an agent evaluation.

Grading:
- grounded answer (strict) = value recovered and no hedging
- value recovered (lenient) = answer contains the key
- evidence available = context or retrieval text contains key plus evidence

8. PERFORMANCE
--------------

- append a small event: 0.56 ms mean per event
- append a 160 KB test log: 36 ms mean (51 ms with indexing inline)
- assemble per turn: 1.35 ms (64k, 45k-token context), 0.74 ms (200k, 68k-token context)
- search, 3.4k chunks: p50 1.45 ms, p95 3.14 ms, p99 3.55 ms (v0.1.0: p95 9.44 ms)
- search, 13.2k chunks: p50 2.78 ms, p95 6.47 ms, p99 6.91 ms (v0.1.0: p95 33.73 ms, which missed the 20 ms target; two term-pruning bugs and a per-candidate stale check were the cause; fixed in v0.1.1 with all deterministic benchmark fields unchanged)
- 4 concurrent agents, 150 turns each: append p95 9.29 ms, assemble p95 9.59 ms, no cross-agent search hits


9. ACCEPTANCE TARGETS
---------------------

- exact recovery of committed events: no failure observed (Verify after every engine run; crash test with SIGKILL)
- protected constraints preserved: no failure observed in runs with pins
- tool-call protocol corruption: no failure observed (validated per assembly and in adapters; live only via OpenRouter)
- cross-agent or cross-session leakage: no failure observed in tested configurations
- context-overflow requests: none observed for G and its ablations
- synchronous summarization in normal operation: none (G's foreground wait is 0 s)
- small-event overhead under 20 ms p95: met
- lexical retrieval under 20 ms p95: met at 3.4k chunks, missed at 13.2k
- at least 50% fewer tool-output tokens: met against summary-only strategies at 64k, partly at 200k (counts all tool tokens; "unnecessary" was not defined)
- task success: NOT EVALUATED


10. THREATS TO VALIDITY
-----------------------

- I built both the workload and the engine; the workload targets the problems the engine was designed for.
- The trajectory is fixed; real task success could differ in either direction.
- The retrieval policy uses one hand-written query per fact.
- Cache costs are simulated; output tokens of the main agent are excluded.
- Baselines are reconstructions. The extractive summarizer is weak, which hurts summary-only baselines most.
- Small samples, no significance tests.
- The v2 grading changes were made after seeing v1. v3 was pre-registered.


11. QUESTIONS FOR THE REVIEWER
------------------------------

1. Does the corrected accounting (section 4, accounting tables) now look consistent? Check that cache read + write + uncached = input Mtok, and that the costs follow from the prices in section 3.
2. Does the component-matched comparison (section 5) support this conclusion? Once baselines get retrieval, G's remaining advantages are:
   - lower cost (about half of E or F plus retrieval)
   - standing-rule retention (pins)
   - recall of the current failure (task state)
   - no blocking, compared with E
   and not general fact recovery.
3. Is the v3 frozen protocol sound? Is anything in its design favorable to G?
4. The ablations suggest most efficiency comes from controlling what enters the context (externalization, masking cadence, cache layout) rather than better summaries. Is that a defensible central claim?
5. What is the minimum real-agent experiment that would convince you? Please name concrete tasks, sample size, models, and the metrics to report.
6. Is anything internally inconsistent or suspicious?
